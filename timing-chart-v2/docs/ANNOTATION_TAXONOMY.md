# Timing-specification annotation taxonomy

Status: proposed design disposition for #1092, based on the current schema and command owners; product approval is still required before adding new canonical types. This document does not add canonical types or claim implementation of future Setup/Hold constraints.

## Dispositions

| Candidate | Canonical meaning | Anchor / time semantics | Checker relation | Presentation / export | Decision |
|---|---|---|---|---|---|
| Delay / latency | An observed interval is a `Measurement`; an allowed interval is a latency `Constraint`. They answer different questions and must not be one overloaded object. | Measurements use two `SemanticAnchor`s; latency constraints use stable trigger/response signal IDs and edges plus min/max cycles. Physical readout uses the document `PhysicalTimebase`; source coordinates remain cycles. | Latency range is checkable; an observed Measurement is descriptive input to review, not itself a pass/fail rule. | Measurement owns its existing label/markers/layout and SVG export. Constraint results belong in Problems. | MERGE into Measurement + Constraint; no new annotation subtype. |
| Setup window | A requirement that data be stable for a minimum interval before a capture edge. | A future typed constraint must identify the data signal, capture clock/edge, and the measured source-time interval. Conversion to physical units requires `PhysicalTimebase`. | Yes; emit a source-linked Problem when the required interval is violated. | A visual window may be projected from the check result or represented by an existing Timing Region; it is not an independent semantic owner. Export the derived visual only when explicitly requested. | KEEP as a distinct constraint semantic; define in a bounded follow-up before implementation. |
| Hold window | A requirement that data remain stable for a minimum interval after a capture edge. | Same identities as Setup, but the interval is post-edge; store source-cycle/edge semantics, not pixel geometry. | Yes; emit a source-linked Problem on violation. | Same separation as Setup: check semantics in Constraint, optional display through existing Timing Region/Problem reveal. | KEEP as a distinct constraint semantic; define with Setup in a bounded follow-up. |
| Valid window | A manually authored interval can use `TimingRegion`; protocol validity derived from signals is a checker result, not an annotation. | TimingRegion uses its existing start/end semantic anchors. A derived protocol window is keyed to stable signal IDs and source cycles. | Only the derived protocol rule is checkable. A manually drawn region is descriptive. | Existing TimingRegion rendering/export is sufficient for descriptive windows; no second range model. | MERGE into TimingRegion or the relevant checker rule according to intent. |
| Don't care | An unknown/not-constrained waveform value, not a timeline annotation. | Use the existing signal value domain at the affected source cycle. Do not encode it as a text label or screen overlay. | It is input semantics; checks decide whether unknowns are permitted in context. | Existing waveform rendering and export display the value. | MERGE into signal values/check policy; no annotation type. |
| Expected | An expected waveform/state belongs to a Scenario; a requirement that the waveform satisfy belongs to a Constraint. | Scenario signal state is keyed by stable `SignalId`; comparisons use source time. | Scenario comparison reports differences; Constraints express pass/fail requirements. | Existing scenario difference/reveal presentation owns overlays; export follows the selected scenario/comparison contract. | MERGE into Scenario + Constraint; no annotation type. |
| Error / warning | A diagnostic result with severity and source context. | A Problem may identify entity IDs and a source cycle; it is derived rather than user-authored timeline truth. | This is the output of validation/checking. | Problems owns severity styling, navigation and diagnostics output; do not persist an annotation copy. | MERGE into Problems. |
| Cause / effect | A visual dependency is not proof of causation. Existing Dependency annotation is a presentation relationship only. | Existing stable semantic anchors describe the endpoints. A future causal model would need typed source/target entity references and rule semantics. | No checker meaning is implied by a Dependency glyph. | Existing Dependency route/arrow rendering/export is appropriate for an authored visual relation. | MERGE into Dependency for presentation; do not claim causal analysis. |
| Protocol violation | A failed protocol rule, not a new annotation. | The violated Constraint and stable signal IDs/source cycle identify the finding. | Yes; this is a Problem derived from protocol checks. | Problems provides navigation/reveal; an optional TimingRegion may highlight the affected interval without duplicating the result. | MERGE into Constraint + Problems. |
| Requirement | External traceability identity/metadata, not a timing interval by itself. | No timeline anchor unless a separate, explicit mapping links the requirement to a signal, interval, or constraint. | Requirements may link to checks but do not define checker behavior by their name alone. | Existing Text/Callout may provide explanatory prose; it must not be treated as structured traceability. | DROP from the annotation taxonomy. If release needs traceability, define a separate requirement-link model and owner first. |

## Visual notation disposition

The notation below deliberately reuses existing rendering owners. It is a
design direction, not a claim that future checker visuals are implemented.

| Candidate | Proposed visual notation | Existing owner / rule |
|---|---|---|
| Delay / observed latency | Existing Measurement endpoint extensions, dimension line, and numeric delta label; an allowed latency is not drawn as an observed measurement. | Measurement presentation; a failed latency Constraint is reported through Problems. |
| Setup window | A lightly shaded interval immediately before the selected capture edge, with the capture edge and required duration identifiable; violations use the Problem severity marker. | Future Setup Constraint projection, optionally using TimingRegion styling; never a second persisted annotation. |
| Hold window | A lightly shaded interval immediately after the selected capture edge, visually distinct by its post-edge placement; violations use the Problem severity marker. | Future Hold Constraint projection, optionally using TimingRegion styling. |
| Valid window | Existing translucent TimingRegion band for an authored interval. A protocol-derived valid interval is a checker result and is not automatically authored. | TimingRegion or derived Problem, according to origin. |
| Don't care | Existing waveform X/Z/unknown value glyph at the source cycle; no overlay badge. | Signal value renderer and the relevant check policy. |
| Expected | Existing Scenario comparison/ghost-trace waveform, visually differentiated from the authored trace (for example dashed, muted stroke). | Scenario comparison projection; not a new annotation shape. |
| Error / warning | Problems severity icon and source-linked reveal/highlight; severity is not encoded by an independently editable annotation. | Problem diagnostics and navigation. |
| Cause / effect | Existing labeled Dependency arrow between stable anchors, explicitly understood as a visual relation only. | Dependency annotation renderer; it does not assert causality. |
| Protocol violation | Problems severity and source-linked interval/signal reveal; an optional TimingRegion may shade the interval only when the user explicitly requests presentation. | Constraint checker + Problem; optional TimingRegion remains a separate authored view annotation. |
| Requirement | No timeline glyph by default. A future approved traceability feature should show an external requirement key in its own linked-requirement surface, not as a generic timing shape. | Separate traceability owner required; Text/Callout remains explanatory prose. |

## Ownership and lifecycle rules

- Keep canonical time in source cycles. Convert to seconds/submultiples only through `PhysicalTimebase`; never persist screen X as annotation meaning.
- Keep observed Measurements, authored Timing Regions, checkable Constraints, derived Problems, and Scenario expectations distinct. A visual overlay may present one of these owners but must not become a second semantic source of truth.
- `Range` and `Highlight` remain generic authored presentation annotations: they may mark an interval for review, but they do not state that a protocol is valid, define a setup/hold requirement, or own a checker result. `TimingRegion` is the existing semantic interval owner when the interval itself is meaningful; `Constraint` owns a checkable requirement; `Problem` owns its derived finding.
- Any future Setup/Hold implementation must use stable signal identities, a typed SemanticCommand, schema validation, exact Undo/Redo and Save/Open, and source-cycle-aware export/reveal behavior.
- Problems, Expected/Scenario data, and Don't-care signal values must not create duplicate Annotation records merely to obtain color or geometry.
- A future Requirement traceability feature requires its own approved stable identity/reference contract; a text label is not a substitute.

## Persistence, history, export and AI contract

| Candidate / disposition | Save / Open | Undo / Redo | Export | AI operation policy |
|---|---|---|---|---|
| Delay / latency → Measurement or Constraint | Measurement anchors and latency bounds persist under their existing canonical owners; Open validates the same stable references. | Existing Annotation or Constraint semantic command is one atomic history unit; undo restores exact anchors/bounds. | Measurement presentation exports through ExportScene; a latency finding remains a diagnostic and is not silently drawn as a user-authored shape. | AI may propose typed Measurement/Constraint commands with stable endpoints/IDs; it cannot write a derived pass/fail result as canonical data. |
| Setup / Hold → future typed Constraint | Persist typed edge/signal/bound data in Constraint; validate references and units on Open. | One typed create/update/delete command per accepted action; Undo restores the prior exact constraint. | Export any derived interval only as an explicit Problem/reveal or TimingRegion projection, never as a second canonical interval. | Not available until a typed schema/command is accepted; then AI may propose those typed commands and normal validation/approval applies. |
| Valid window → TimingRegion or checker | Authored TimingRegion anchors persist; checker output is recomputed from signal/constraint data after Open. | TimingRegion edits use annotation commands; derived checker findings do not create history entries. | Export the authored region; derived Problems follow diagnostic-export policy. | AI may create/update a TimingRegion or propose a typed check constraint, but may not persist a checker result. |
| Don't care → Signal value | Persist as the appropriate canonical signal transition/value and retain its source cycle. | The existing signal value semantic command is one operation; Undo restores the previous transition/value sequence. | Waveform/export reads the canonical value; no additional annotation layer is required. | AI may propose a typed value edit; schema and signal-type validation decide whether the value is legal. |
| Expected → Scenario / Constraint | Scenario-owned signal states and any relevant constraints persist in their current owners. | Scenario/value edits use their existing semantic commands; comparison output is recomputed, not undone as a separate entity. | Export the selected Scenario or an explicit comparison view. | AI may propose typed Scenario or Constraint edits; it cannot store comparison differences as expected waveform truth. |
| Error / warning → Problem | Derived Problems are not serialized as canonical annotations; rerun checks after Open. | No Problem history unit. Undo/Redo applies to the source edit or Constraint that caused the finding. | Use the diagnostics export/review path; never duplicate a finding into an Annotation automatically. | AI may explain a Problem or propose a typed correction; it cannot author/change Problem severity or claim a check passed. |
| Cause / effect → Dependency presentation | Dependency anchors/type-specific route persist as an Annotation and round-trip through existing Save/Open. | Existing annotation semantic commands provide exact one-operation Undo/Redo. | Existing Dependency SVG/export semantics apply. | AI may create an explicitly labeled visual dependency; it must not infer or claim causal proof. |
| Protocol violation → Constraint / Problem | Persist the source Constraint; recompute the violation Problem after Open. | Undo/Redo changes the authored Constraint or source signal data, not a derived Problem. | A Problem may be included in diagnostics output; any visual interval is a separate, explicitly requested projection. | AI may propose a typed Constraint or source-data correction; only the checker may produce the violation result. |
| Requirement → DROP from annotation taxonomy | No requirement link is persisted by this disposition. A future traceability feature needs its own stable requirement identity/reference schema. | No Annotation or history behavior is implied. A future requirement link must define its own one-command lifecycle. | A future traceability owner must specify linked requirement export; Text/Callout export is explanatory prose only. | No structured AI operation until a requirement-link owner and typed command exist; AI-generated prose is not a traceability link. |

These lifecycle dispositions describe where a candidate would live; they do not assert that future Setup/Hold or Requirement features already exist. No AI route may bypass schema validation, typed SemanticCommands, or the normal approval policy.

## Current code evidence

- `packages/schema/src/types.ts`: `Measurement`, `TimingRegion`, `Dependency`, `Constraint`, `Problem`, `TimingScenario`, and `PhysicalTimebase` are distinct existing owners.
- `packages/commands/src/planner.ts`: `constraint.createLatency` already records stable trigger/response signal IDs, edges, and cycle bounds.
- `packages/schema/src/scenario-model.ts`: Handshake constraints drive deterministic missing-case suggestions and source-signal-aware scenario checks.
- `packages/export/src/index.ts`: Annotation geometry and presentation export through `ExportScene`; check findings remain diagnostics rather than annotations.

This is a roadmap disposition, not evidence that Setup/Hold checker semantics or Requirement traceability are implemented. Such work must be separately scoped and accepted before production changes.
